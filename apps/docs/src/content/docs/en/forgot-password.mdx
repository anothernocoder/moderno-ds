**Forgot password** is the third entrance of the auth flow, and the first screen
with two states of its own. It is a full-viewport composition of the
[login form](/en/login-form/) in its `forgot-password` mode — the address, and
nothing else — and the [alert list](/en/alert-list/) carrying the notes that
answer the question everyone asks next: it has not arrived, now what?

The two states are one card. Unsent it asks; sent it confirms, in the same card,
in the same place, with the masthead, the notes and the footer exactly where
they were. A recovery page that re-lays itself out at the moment of confirmation
makes the reader find it again precisely when they have been told to go and look
somewhere else.

Like every screen it is presentational: it owns the viewport and nothing else.
No address, no request, no router — and not even `sent`, because whether the
mail went out is something only the request knows.

## Installation

<Install item="forgot-password" />

Installing a screen installs the blocks it composes — here `login-form` and
`alert-list`, both of which `sign-in` also uses — and records each under its own
version in `.moderno/manifest.json`, so `moderno update` and `moderno diff` keep
working per item. Installing all three auth screens therefore lands one copy of
the card, not three. Nothing is pulled in upward: this screen arrives without
the `auth` flow it belongs to.

The screen imports its blocks from `@/components/blocks/…`, which is where
`moderno add` writes them. If your project maps `@/` somewhere other than `src/`,
those import lines are the only edit.

## It never confirms that an account exists

The confirmation says **"if that address has an account, a link to set a new
password is on its way"**, and the screen renders exactly the same card whether
one does or not. That is not politeness. A recovery form that says "we sent you
a link" for a known address and "we have no such user" for an unknown one is an
account-enumeration endpoint: an attacker walks a list of addresses through it
and learns which ones are worth a credential-stuffing run.

The screen can only keep half of that promise — the half that is markup. The
other half is yours: the code behind `onSubmit` has to answer with the same
response, and in the same time, for an address that exists and one that does
not. Rate-limit the endpoint by address _and_ by caller, and do the mail send
out of band so a slow SMTP hop cannot be timed.

`errors.email` is the one thing this screen will say about the address: that it
is not a valid address at all. Being told your typo is a typo leaks nothing.

## Sizing

Full-viewport is a **height** — the root is `min-h-dvh`. Every _width_ decision
is read off the screen's own container, so it is still right in a pane that is
not the window: an Electron content area, a preview frame, an embedded console.

| Step  | Slot             | What changes                                                                |
| ----- | ---------------- | --------------------------------------------------------------------------- |
| `@sm` | `--container-sm` | The masthead stops stacking: the wordmark and the support link share a row. |
| `@md` | `--container-md` | The footer stops stacking: the copyright and the legal links share a row.   |
| `@lg` | `--container-lg` | The notes leave their place under the card and stand beside it.             |

None of that reads the window, which is why the three frames above disagree
with each other on one screen. The rules behind this are in
[Blocks and containers](/en/blocks-and-containers/) and ADR-0005.

Both blocks inside go on reading _their own_ containers, one level down: the
card caps itself at `--container-sm` however much room the screen gives it, and
at `@lg` the notes get half the row — narrow enough that each note's dismiss
control is still in its glyph-only mode while the screen around it is at its
widest. Neither block knows it was mounted in a screen.

## The outline, and what is said out loud

The screen is the whole route, so it carries the page's `h1` — and the `h1` is the
card's own title, handed down as `titleLevel={1}`, because "Reset your password"
is what the page is called. The notes beside it print the `h2`. There is no second
heading stacked above the card to satisfy an outline: the outline is the card,
then the notes, in that order at every width.

The confirmation is announced as well as shown. `sent` rewrites the card's header
where it stands — nothing moves, which is the point — so the header is a live
region from the moment the card mounts. Without it the only signal that the link
went out is that the button just pressed has renamed itself, which reads as a
failure more than a confirmation.

## States

| State         | What renders                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Default       | The card asking for the address, and beside or under it the notes.                                                                    |
| Sent          | `sent` — the same card, confirming, with `sentTo` named in the sentence and carried in a hidden input so the resend works unhydrated. |
| Error         | `error` — the form-level alert: the link could not be sent at all.                                                                    |
| Field error   | `errors={{ email: "…" }}` — the address is malformed; that field goes invalid and prints its own message.                             |
| Loading       | `loading` — every control inert, the submit marked `aria-busy`, its spinner stopped under `prefers-reduced-motion`.                   |
| Disabled      | `disabled` — recovery is unavailable here at all (an SSO-only workspace, a locked account).                                           |
| Notes loading | `noticesLoading` — a busy region stands in for the list rather than a stale one under a spinner.                                      |
| Notes error   | `noticesError` — the notes could not be loaded, said out loud rather than shown as an empty column.                                   |
| Empty         | `notices={[]}` — nothing to warn about, so the aside is not rendered at all and the card sits centred and alone.                      |
| Focus visible | The shared 2px `--ring` outline on every field, control and link, in the reading order of the page: masthead, card, notes, footer.    |

## Props

| Prop             | Type                     | Default       | What it does                                                                                                                       |
| ---------------- | ------------------------ | ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `sent`           | `boolean`                | `false`       | The link has gone out: the card confirms instead of asking.                                                                        |
| `sentTo`         | `string`                 | `""`          | The address the link went to — named in the confirmation, resubmitted by "Send it again".                                          |
| `error`          | `string`                 | —             | The link could not be sent at all: raises the form-level alert.                                                                    |
| `errors`         | `Record<string, string>` | —             | Per-field messages keyed by the field's `name` (here, `email`).                                                                    |
| `loading`        | `boolean`                | `false`       | The submit is in flight: every control inert, the button busy.                                                                     |
| `disabled`       | `boolean`                | `false`       | Recovery is unavailable.                                                                                                           |
| `notices`        | `AlertListItem[]`        | three samples | The notes shown beside the card. `[]` renders the card alone.                                                                      |
| `noticesError`   | `string`                 | —             | The notes could not be loaded; that message replaces the list.                                                                     |
| `noticesLoading` | `boolean`                | `false`       | A busy region stands in for the notes.                                                                                             |
| `onSubmit`       | `(event) => void`        | —             | Native submit — the request _and_ the resend. React/Solid `onSubmit`, Svelte `onsubmit`, Vue emits `submit`.                       |
| `onNavigate`     | `(to, event) => void`    | —             | A link the screen draws itself was activated: `home`, `support`, `privacy` or `terms`, with the click event. Vue emits `navigate`. |
| `signInHref`     | `string`                 | `"#"`         | Where "Sign in" points, in the card's footer.                                                                                      |
| `homeHref`       | `string`                 | `"#"`         | Where the wordmark points.                                                                                                         |
| `supportHref`    | `string`                 | `"#"`         | Where "Contact support" points.                                                                                                    |
| `privacyHref`    | `string`                 | `"#"`         | Where the privacy link points.                                                                                                     |
| `termsHref`      | `string`                 | `"#"`         | Where the terms link points.                                                                                                       |

The notes also report themselves: `onNoticeAction`, `onDismissNotice`,
`onDismissNotices` and `onRetryNotices` are forwarded straight to the block, the
same four the [sign-in screen](/en/sign-in/) passes.

`sent` lives in the page, not here, and one handler covers both submits:

```tsx
const [sent, setSent] = useState(false);
const [address, setAddress] = useState("");

<ForgotPassword
  sent={sent}
  sentTo={address}
  loading={pending}
  onSubmit={async (event) => {
    event.preventDefault();
    const email = String(new FormData(event.currentTarget).get("email"));
    setAddress(email);
    await requestReset(email); // same response, same timing, every address
    setSent(true);
  }}
/>;
```

The resend goes through that same handler because the sent card carries the
address in a hidden input — which is also why it still works on a page whose
JavaScript never arrived.
