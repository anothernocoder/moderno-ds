**Reset password** is the far end of the link the
[forgot-password screen](/en/forgot-password/) sends. It is a full-viewport
composition of the [login form](/en/login-form/) in its `reset-password` mode —
a new password, its confirmation, and the rules ticking off as they are met —
and the [alert list](/en/alert-list/) carrying the three things worth knowing
before that password is chosen.

It asks for one thing, twice, and never for the old password: whoever is here
followed a link from an email precisely because they do not have it. The token
out of that link travels inside the form, so the reset posts on a page whose
JavaScript never arrived.

Like every screen it is presentational: it owns the viewport and nothing else.
No value, no request, no router, and no verdict on the token — whether the link
is still good is something only the request knows.

## Installation

<Install item="reset-password" />

Installing a screen installs the blocks it composes — here `login-form` and
`alert-list`, the same two `sign-in` and `forgot-password` use — and records each
under its own version in `.moderno/manifest.json`, so `moderno update` and
`moderno diff` keep working per item. Installing all four auth screens therefore
lands one copy of the card, not four. Nothing is pulled in upward: this screen
arrives without the `auth` flow it belongs to.

The screen imports its blocks from `@/components/blocks/…`, which is where
`moderno add` writes them. If your project maps `@/` somewhere other than `src/`,
those import lines are the only edit.

## The rules are said, not enforced

`requirements` is a list of `{ id, label, met }`. The card renders it as the
new-password field's **own helper text**, which is what puts it in that input's
`aria-describedby`: the rules are read on focus, before anything has been typed,
rather than discovered after the form comes back rejected. The list is a polite
live region, so the one rule that turns green announces its own line and leaves
the others alone, and every row doubles its tick with the word "met" — a rule you
can only tell has passed by its colour has not been said to everyone.

`met` is not computed here. The screen holds no value — that is what
presentational means — so the page that mounts it recomputes the flags as the
reader types:

```tsx
const [value, setValue] = useState("");

<ResetPassword
  token={token}
  requirements={[
    { id: "length", label: "At least 12 characters", met: value.length >= 12 },
    {
      id: "case",
      label: "An upper and a lower case letter",
      met: /[a-z]/.test(value) && /[A-Z]/.test(value),
    },
    { id: "symbol", label: "A number or a symbol", met: /[^A-Za-z]/.test(value) },
  ]}
  onSubmit={async (event) => {
    event.preventDefault();
    const form = new FormData(event.currentTarget);
    await completeReset(String(form.get("token")), String(form.get("password")));
  }}
/>;
```

None of it is a gate. The card does not block a submit, and it should not: the
server has to apply every one of these rules again, because a rule enforced in
the browser is a rule an attacker walks around. What the markup does buy you is
that with no JavaScript on the page the rules are still printed, the token still
rides in the form, and the reset still posts.

## The token, and the link that is spent

`token` is the value out of the link's query string, and the card puts it in a
hidden input inside the `<form>`. So the reset is a plain form submission: read
it back out of `FormData` alongside the password, exactly as the example above
does. A reset page that only works once a bundle has hydrated strands the person
it was written for — someone already locked out, quite possibly on a phone with
one bar.

A link that has expired, or has already been used, is **`error` plus
`disabled`** — never a field message. What went wrong is the token, and marking
`password` invalid sends the reader off to fix something that was never broken.
The screen says so and stops taking a password, and the masthead's "Link
expired? Contact support" is right there.

## Sizing

Full-viewport is a **height** — the root is `min-h-dvh`. Every _width_ decision
is read off the screen's own container, so it is still right in a pane that is
not the window: an Electron content area, a preview frame, an embedded console.

| Step  | Slot             | What changes                                                                |
| ----- | ---------------- | --------------------------------------------------------------------------- |
| `@sm` | `--container-sm` | The masthead stops stacking: the wordmark and the support link share a row. |
| `@md` | `--container-md` | The footer stops stacking: the copyright and the legal links share a row.   |
| `@lg` | `--container-lg` | The notes leave their place under the card and stand beside it.             |

None of that reads the window, which is why the three frames above disagree with
each other on one screen. The rules behind this are in
[Blocks and containers](/en/blocks-and-containers/) and ADR-0005.

Both blocks inside go on reading _their own_ containers, one level down: the card
caps itself at `--container-sm` however much room the screen gives it, and at
`@lg` the notes get half the row. Neither block knows it was mounted in a screen.

## The outline

The screen is the whole route, so it carries the page's `h1` — and the `h1` is
the card's own title, handed down as `titleLevel={1}`, because "Choose a new
password" is what the page is called. The notes beside it print the `h2`. There
is no second heading stacked above the card to satisfy an outline: the outline is
the card, then the notes, in that order at every width.

## States

| State         | What renders                                                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Default       | The card asking for a new password and its confirmation, the rules unticked, the notes beside or under it.                         |
| Rules met     | `requirements` with `met` — each row that flips is announced on its own; the tick is doubled by the word "met".                    |
| Error         | `error` — the form-level alert. The spent or expired link belongs here, with `disabled`.                                           |
| Field error   | `errors={{ confirmPassword: "…" }}` — that field goes invalid and prints its own message.                                          |
| Loading       | `loading` — every control inert, the submit marked `aria-busy`, its spinner stopped under `prefers-reduced-motion`.                |
| Disabled      | `disabled` — no password can be set here at all; pair it with `error` so the screen says why.                                      |
| Notes loading | `noticesLoading` — a busy region stands in for the list rather than a stale one under a spinner.                                   |
| Notes error   | `noticesError` — the notes could not be loaded, said out loud rather than shown as an empty column.                                |
| Empty         | `notices={[]}` — nothing to say about the link, so the aside is not rendered at all and the card sits centred and alone.           |
| Focus visible | The shared 2px `--ring` outline on every field, control and link, in the reading order of the page: masthead, card, notes, footer. |

## Props

| Prop             | Type                     | Default        | What it does                                                                                                                       |
| ---------------- | ------------------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `token`          | `string`                 | `""`           | The token out of the emailed link, submitted with the password from a hidden input.                                                |
| `requirements`   | `PasswordRequirement[]`  | three unticked | The rules under the new password (`{ id, label, met }`); recompute `met` as the reader types.                                      |
| `error`          | `string`                 | —              | Form-level failure: the link has expired, has been used, or the save failed.                                                       |
| `errors`         | `Record<string, string>` | —              | Per-field messages keyed by the field's `name` (`password`, `confirmPassword`).                                                    |
| `loading`        | `boolean`                | `false`        | The submit is in flight: every control inert, the button busy.                                                                     |
| `disabled`       | `boolean`                | `false`        | No password can be set here; pair it with `error`.                                                                                 |
| `notices`        | `AlertListItem[]`        | three samples  | The notes shown beside the card. `[]` renders the card alone.                                                                      |
| `noticesError`   | `string`                 | —              | The notes could not be loaded; that message replaces the list.                                                                     |
| `noticesLoading` | `boolean`                | `false`        | A busy region stands in for the notes.                                                                                             |
| `onSubmit`       | `(event) => void`        | —              | Native submit. React/Solid `onSubmit`, Svelte `onsubmit`, Vue emits `submit`.                                                      |
| `onNavigate`     | `(to, event) => void`    | —              | A link the screen draws itself was activated: `home`, `support`, `privacy` or `terms`, with the click event. Vue emits `navigate`. |
| `signInHref`     | `string`                 | `"#"`          | Where "Sign in" points, in the card's footer.                                                                                      |
| `homeHref`       | `string`                 | `"#"`          | Where the wordmark points.                                                                                                         |
| `supportHref`    | `string`                 | `"#"`          | Where "Contact support" points.                                                                                                    |
| `privacyHref`    | `string`                 | `"#"`          | Where the privacy link points.                                                                                                     |
| `termsHref`      | `string`                 | `"#"`          | Where the terms link points.                                                                                                       |

The notes also report themselves: `onNoticeAction`, `onDismissNotice`,
`onDismissNotices` and `onRetryNotices` are forwarded straight to the block, the
same four the [sign-in screen](/en/sign-in/) passes.

The card's "Sign in" link is an `href`, not a callback — someone who has just set
a password should be able to walk to the sign-in page whether or not the bundle
loaded. Pass `signInHref`.
