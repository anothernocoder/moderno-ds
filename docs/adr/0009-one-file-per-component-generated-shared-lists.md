# One file per component; shared lists are discovered or generated

Extends the pattern of [ADR-0007](0007-default-theme-single-source-and-type-scale.md)
and [ADR-0008](0008-token-system-one-source-per-concept.md) — one hand-edited
source, the rest generated and checked — from tokens to component registration.

## Context

By the time of this ADR, adding a Primitive, Block, Screen or Flow meant
appending an entry to the same ~25 shared files: `components.css`,
`recipes.ts`, the four package barrels, the four playgrounds and SSR suites,
the props-doc manifest and agent examples, the parity matrix, `registry.json`
and several test files.

- **Tickets could not run in parallel.** Any two component tickets edited the
  same lists, so they conflicted on every file. Tickets ran one at a time, about
  25 minutes each, with about 80 left.
- **"Keep both sides" merges corrupted files.** A merge that keeps both sides of
  a list is right for the entries and wrong for anything else in the hunk:
  `docs/parity-matrix.md` ended up with its intro paragraph three times and its
  footnotes interleaved, and `packages/vue/playground/app.ts` with its header
  comment twice.
- **Nothing checked a committed theme.** CI ran `pnpm theme:build`, which
  rewrites the committed theme outputs, before the tests that compare them with
  what it renders. A stale theme was fixed in CI's checkout and passed.

## Decision

1. **A component registers itself by adding files of its own.** Every shared
   list becomes a folder with one file per component (a recipe, a stylesheet, a
   playground mount, a parity section, a registry item). A component ticket adds
   files; it does not edit a list.
2. **A shared list is discovered where it is read, or generated.** Discover it
   when the reader can: vitest globs, Astro content collections, `readdir` in a
   Node script. Generate it when the reader cannot, such as a published package
   barrel, the CSS entry, or `registry.json`, which tools and consumers read
   without running our code.
3. **`pnpm gen` writes every generated file** (`tooling/gen`). Each aggregator
   is one module in `tooling/gen/src/aggregators/` that owns one output file: it
   declares the file's path and the glob of its sources, and returns the body.
   `pnpm gen` finds the aggregators with `readdir`, so adding one edits no list,
   and writes each file under the banner
   `Generated by pnpm gen (<aggregator>) from <source glob>. Do not edit by hand.`
   It runs under `node --experimental-strip-types` like the other bins, so it
   uses neither Vite nor `import.meta.glob`, and generated TypeScript uses
   static imports that `tsc`, tsup and a consumer's bundler all read. Entries
   are sorted by slug unless an aggregator says otherwise.
4. **Generated files are committed and checked in CI.** `pnpm gen --check`
   writes nothing and fails, listing each stale file, when a committed file is
   missing, out of date or edited by hand; CI runs it before the build.
   `.gitattributes` marks every output as `linguist-generated=true`, and it is
   itself written by `pnpm gen` from the outputs the aggregators declare. The
   same rule now covers `pnpm theme:build`: CI follows it with
   `git diff --exit-code`, so a stale committed theme fails.
5. **A generated file is never resolved by hand in a merge.** Take either side
   and rerun `pnpm gen` (or `pnpm theme:build` for a theme). A conflict between
   two component tickets then only happens in generated files, and settling it
   takes no judgement.

### Rejected: gitignored generated files

Generating the files at install or build time and ignoring them in git would
remove the conflicts too, without a check in CI. It was rejected because:

- **Every entry point would need `pnpm gen` first.** `tsc`, `vitest` (whose
  registry gate reads `registry/registry.json` from disk), `pnpm lint:registry`,
  the docs dev server, an editor, and an agent reading the repo would all fail
  with a missing file until someone ran it. Committed files work straight after
  a checkout.
- **Reviews would not show the effect.** The diff of a component ticket would
  not show what it adds to a barrel or to `registry.json`, which is what a
  reviewer and the maintainer need to see.

Committing the files keeps all of that, and `pnpm gen --check` removes what
ignoring them would have avoided: a copy that disagrees with its sources.

## Consequences

- Adding a component, or a new kind of generated file, means adding files: a
  component's own files, or one aggregator module. No shared list is edited by
  hand.
- A ticket that changes a source without running `pnpm gen` fails CI with the
  file to regenerate named, instead of shipping a stale list.
- `docs/agents/ticket-workflow.md` lists `pnpm gen --check` among a ticket's
  checks, and the lander settles a conflict in a generated file by rerunning
  its generator.
- A generated file whose type has no comment syntax (JSON) cannot carry the
  banner as a comment; the aggregator that first generates one decides where
  the banner goes.
